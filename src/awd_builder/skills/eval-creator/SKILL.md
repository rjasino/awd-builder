# Eval Creator

Create the routing eval suite for a workflow. The suite is one file for the whole workflow, `evals/routing.yaml`. It tests routing only: given a user request, does the workflow pick the right agent or skill, or none at all?

Do not write checks for output quality, style, or the correctness of what an agent produces. Quality evals are a separate, future step.

## Inputs

- `workflow-plan.yaml` in the project root. It is the source of truth for every agent, skill, and command. Read it first.

## Steps

1. Read `workflow-plan.yaml`. List every agent and skill with its `name` and `description`. Slash commands are invoked explicitly by the user with `/name`, so leave them out of this suite.
2. Find overlaps: pairs of agents or skills whose descriptions could both fit the same request.
3. Write cases in these groups:
   - **Direct** (at least 2 per agent or skill): a request that clearly belongs to that component, phrased the way a user would type it.
   - **Indirect** (at least 1 per agent or skill): a request that needs the component but does not name it or use its main keyword. For example, "can you look over my diff before I push" for a code-review skill.
   - **Disambiguation** (at least 1 per overlapping pair): a request that sounds like one component but belongs to the other. The expected value is the correct one.
   - **None** (at least 3 per workflow): requests no component should handle, such as small talk, general knowledge, or work outside the workflow's domain. Use `expected: none`.
4. Keep prompts self-contained and realistic. Do not use a component's exact name in more than a third of its cases, so the test checks the description and not a keyword match. Vary length and tone.
5. Write `evals/routing.yaml` using the schema below. Create the `evals` folder if it does not exist.
6. Validate before you finish:
   - The YAML parses.
   - Every `id` is unique and kebab-case.
   - Every `expected` is `none`, or `agent/<name>` or `skill/<name>` where `<name>` exists in the plan with that kind.
   - No prompt is empty.
7. Report the case count per group and the path of the file. Then tell the user the next step: run the runner (see Running).

## Schema

```yaml
# Routing evals for the workflow. Generated by eval-creator; edit freely.
workflow: my-workflow
cases:
  - id: code-review-direct-1
    prompt: "Review the changes in src/auth.ts for bugs and missing tests."
    expected: skill/code-review
  - id: code-review-indirect-1
    prompt: "Can you look over my diff before I push?"
    expected: skill/code-review
  - id: planner-direct-1
    prompt: "Break the login feature into tasks I can hand out."
    expected: agent/planner
  - id: none-small-talk-1
    prompt: "What's a good name for a golden retriever?"
    expected: none
```

Rules for the file:

- `expected` is `agent/<name>`, `skill/<name>`, or `none`. Names are lowercase kebab-case and must exist in the plan.
- `id` values are unique across the file. Use `<component>-<group>-<n>`, for example `code-review-direct-1`.
- Use only the fields `id`, `prompt`, and `expected`. The runner reads nothing else.

## Running

The runner is the `awd-builder` CLI, installed on the user's machine. Run:

```
awd-builder evals <project-folder>
```

Add `--dry-run` to print the exact routing prompts without calling the agent. Add `--only <id>` to run one case.
